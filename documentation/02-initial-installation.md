# Initial Wazuh Deployment Attempt

## Overview

The first Wazuh deployment attempt was performed on a Raspberry Pi 5 running Raspberry Pi OS based on Debian 13 (Trixie), ARM64.

The target deployment was a single-node Wazuh environment containing:

- Wazuh Indexer
- Wazuh Manager
- Filebeat
- Wazuh Dashboard

Wazuh version 4.14.x was used during the deployment.

The initial deployment was ultimately removed and rebuilt after configuration and certificate-related issues made the installation unreliable.

---

## Initial Environment

### Hardware

- Raspberry Pi 5
- ARM64 architecture
- 8 GB RAM

### Operating System

- Raspberry Pi OS
- Debian 13 (Trixie)
- ARM64

### Intended Architecture

The Raspberry Pi was intended to host the complete Wazuh server-side infrastructure as a single-node deployment.

The planned architecture was:

    Wazuh Agent
          │
          ▼
    Wazuh Manager
          │
          ▼
    Wazuh Indexer
          │
          ▼
    Wazuh Dashboard

---

## Installation Process

The initial installation followed Wazuh documentation and involved manually installing and configuring the individual components.

The following components were installed during the attempt:

- Wazuh Indexer
- Wazuh Manager
- Filebeat
- Wazuh Dashboard

The Wazuh repository was added to the system and the required packages were installed through APT.

The Indexer, Manager, and Dashboard packages were successfully installed.

---

## Problems Encountered

### 1. Operating System Compatibility

The Wazuh installer reported that the operating system did not match the recommended operating systems.

The Raspberry Pi was running Debian 13/Trixie on ARM64, while the Wazuh installation documentation primarily targeted distributions such as Ubuntu, RHEL/CentOS, Amazon Linux, and Rocky Linux.

The installation was therefore performed manually rather than relying entirely on the assisted installation process.

---

### 2. Certificate and Trust Configuration

The deployment used certificates generated by the Wazuh certificate tool.

Certificates were generated for:

- Wazuh Indexer
- Filebeat
- Wazuh Dashboard
- Administrator access
- Root CA

The certificates were distributed to the appropriate component directories.

During configuration, certificate ownership and permissions also required correction.

For example, wildcard expansion behaved differently when commands were executed through `sudo`. The following approach successfully allowed the shell running as root to expand the wildcard:

    sudo sh -c 'chmod 400 /etc/wazuh-indexer/certs/*'

A similar approach was required for Filebeat certificates.

---

### 3. Repository and Privilege Errors

Several installation commands initially failed because commands that modified system directories or installed packages were executed without sufficient privileges.

Examples included:

- APT package installation without `sudo`
- Writing to `/etc/apt/sources.list.d/`
- Modifying files under `/etc/`
- Extracting certificates into system directories
- Managing systemd services

These failures reinforced the distinction between commands that operate in the user's home directory and commands that require root privileges.

---

### 4. Filebeat Connectivity Test

Filebeat was eventually configured to communicate with the Wazuh Indexer.

The connectivity test demonstrated that several parts of the connection were working correctly:

- URL parsing succeeded
- DNS lookup succeeded
- TCP connection succeeded
- TLS handshake succeeded
- TLS 1.3 negotiation succeeded

However, the final request returned:

    503 Service Unavailable: OpenSearch Security not initialized.

This showed that the problem was no longer basic network connectivity or TLS negotiation. The Indexer was reachable, but OpenSearch Security had not yet been initialized.

---

## Certificate Configuration Problem

During the first deployment, certificate configuration became increasingly difficult to troubleshoot.

A second certificate authority was generated during troubleshooting, which introduced a trust mismatch between components.

Although TLS connectivity could be made to work, authentication subsequently returned:

    401 Unauthorized

This indicated that the system had progressed beyond basic TLS connectivity but still had an authentication/trust configuration problem.

At this point, continuing to modify the partially configured installation risked creating additional configuration inconsistencies.

---

## Decision to Rebuild

Rather than continuing to modify the partially configured installation, the Wazuh components and related configuration were removed.

The decision to rebuild provided a clean environment in which to:

- Follow the Wazuh installation procedure more carefully
- Generate the certificate set only once
- Maintain consistent node names
- Maintain consistent IP addresses
- Verify each component individually
- Document problems and solutions as they occurred

The failed installation was intentionally preserved as part of the project's troubleshooting history.

---

## Lessons Learned

The first deployment provided several practical lessons:

### Understand the Environment Before Installing

The operating system, architecture, supported packages, and installation method should be verified before beginning a deployment.

### Certificates Are Infrastructure

TLS certificates are not simply files that can be regenerated whenever something goes wrong.

The certificate authority and trust relationships between components must remain consistent.

### Verify Each Layer Independently

A successful TLS handshake does not necessarily mean an application is fully operational.

The Filebeat test demonstrated this clearly:

    Network connection       → successful
    TLS handshake            → successful
    OpenSearch Security      → not initialized
    Application request      → HTTP 503

Testing each layer independently makes troubleshooting much more systematic.

### Root Privileges Matter

Many of the early errors were caused by commands attempting to modify protected system resources without root privileges.

Understanding why `sudo` is required is more useful than simply adding `sudo` to every command.

### Rebuilding Can Be the Correct Troubleshooting Decision

When configuration changes begin introducing additional variables, rebuilding from a known state can be more efficient than continuing to troubleshoot an increasingly inconsistent installation.

---

## Outcome

The initial deployment was unsuccessful and was removed.

A second deployment was subsequently performed using a cleaner installation process.

The second deployment successfully established the centralized Wazuh infrastructure and became the baseline for the remainder of the project.

The failed deployment remains documented because it demonstrates the troubleshooting and systems-administration process involved in building the lab.
